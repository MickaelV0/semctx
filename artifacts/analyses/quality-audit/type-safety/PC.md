# Type safety — PC

## Summary
Reviewed Plane C production source only (`packages/control-model/src`, `packages/control-engine/src`, `packages/change-authorization-verifier/src`; 52 `.ts` files). There is no `: any`, `as any`, `@ts-ignore` / `@ts-nocheck` / `@ts-expect-error`, or `JSON.parse`. Health is otherwise uneven: control-model is a Zod + branded-hash kernel, but the engine’s graph/hunk boundary type-launders `unknown` with `as unknown as` instead of `CoordinateGraphReportV2Schema` / `ObservedDiffHunkV1Schema`, and the rest of the partition leans on `as unknown as z.ZodType<T>`, `parse() as T`, `as never`, and postfix `!`. Worst issue is `parseCoordinateGraphV2` returning a hand-checked record as `CoordinateGraphReportV2` while a stricter Zod contract already exists.

## Recommendations
1. Land TYPE-PC-01 first. The graph-in boundary must be the Zod contracts in `refinement-schemas.ts`, not a second parser that returns `as unknown as T`.
2. Reorder `ExecutionStateSchema` so `authorizeStep` can use inferred `parsed.data` with no recast.
3. Stop exporting schemas as `as unknown as z.ZodType<T>`. Prefer `satisfies` + `z.infer` so TYPE-PC-05 recasts disappear mechanically.
4. Add `never` defaults on `CandidateSourceChangeV1`, repository-edit `kind`, binding `scope.kind`, and graph `schemaVersion`.
5. Replace postfix `!` on `Map.get` / optional array elements with get-or-throw or `.filter` narrowing; leave index-`!` in `for (index = 1; …)` loops for last.
6. Do not introduce `JSON.parse` or `z.any()` on these paths. Verifier may stay Zod-import-free; it still must construct reports from narrowed fields rather than asserting the input object.
